# 底线规则（各 skill 共用）

这几条决定读者能不能信任产出。形式再好，违反其中一条，产出就不能用。

## 1. 答案先行

第一句给读者最需要的东西：结论、状态、或要他做的决定。读者常常只读第一句。

## 2. 意思不变

改写、摘要、画图、做页面，都不能改变原文的意思。下面这些最容易在「变清楚」的过程中走样，要逐项守住：

- **数字和单位**：百分点不是百分比；「约」「不超过」「以上」都是意思的一部分。
- **条件和例外**：例外常常写在离规则很远的地方，摘要时最容易丢。
- **否定**：双重否定可以改成肯定，但必须等价。
- **确定程度**：「预计」「初步」「尚未验证」「可能」不能升级成断言，也不能反过来。
- **归属和分歧**：谁说的、谁反对、最后有没有定。「张三认为」不是「已决定」。
- **状态**：提议、已决定、已完成、已验证是四件不同的事。
- **口径**：含不含税、含不含某项成本、统计范围。

原文内部有矛盾（比如表格和正文的数字不一致），**指出来，不要替它改**。你不知道哪个是对的。再往下查一步：原文里哪些结论、建议是建立在这个数字上的？它们也要一起标出来，不能照搬。

## 3. 不加原文没有的事实

不补原因，不补原文没有的日期、选项、建议，不补「（待确认）」这类原文没有的注释，也不把「希望」「倾向」升格成「计划」「决定」。原文本身标了不确定，就照样标。

下面两种不算添加，可以做：

- 指出原文的矛盾，或说明本稿按哪一处写。
- 为了让读者明白「这对我意味着什么」，按原文的条件算一个例子（比如违约时能抵扣多少钱）。要算对，并标明「按原文条款推算」。只在读者需要时算，不要为了显得具体而算。

## 4. 不虚报

没渲染就不说「看过」，没运行就不说「通过」，没打开的网页不放链接。工具缺失时，明说降级成了什么。

## 5. 不硬升级形式

一段文字能讲清楚，就不画图；一张图能讲清楚，就不做页面。只在当前形式确实遮住了读者要判断的东西时，用一句话提议换更重的形式，并说明可以用哪个 skill（`zh-ladder-diagram` 讲解图、`zh-ladder-page` 交互页），用不用由读者决定。不同 agent 调用 skill 的写法不一样，说清 skill 名字即可，不要写死某个产品的命令格式。

## 6. 交付物留在本地

产出写进用户指定的位置，用户没指定时写进系统临时目录，**不外发**：不上传云盘、不发布成在线页面、不把材料贴进第三方服务、不在交付的页面或图里引用需要联网才能显示的资源。要不要分享给别人，由用户自己决定和操作。

这条在材料看起来是内部内容时优先于任何「更方便」的交付方式。检查脚本报告的外部请求只是线索，不构成隔离：页面发出去什么，取决于页面里写了什么。
