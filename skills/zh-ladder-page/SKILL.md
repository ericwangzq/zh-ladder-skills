# 中文交互讲解页

目标：读者自己动手改一个值，就看出规则或机制是怎么运作的，并且能把页面上的每个结论对回原文。

交互页做得好，读者会比读文字更快、更深地理解；做得不好，它只是一个更花哨、更难核对的文字版。精美的页面也更容易让错误显得可信。所以这里一半的规则是为了让页面真正需要「动手」，另一半是为了让它可以被核对。

先读底线规则：`${CLAUDE_SKILL_DIR}/references/底线.md`。

## 用法

本 skill 只在用户手动调用时运行（`/zh-ladder-page`，pi 里是 `/skill:zh-ladder-page`）。命令后面的文字就是任务；要讲解的材料（文件路径或粘贴的文字）没给就先问一句，不要自己找。

## 1. 先决定要不要做

只在读者需要**改一个值看结果**时做：取决于他自己情况的规则（能拿多少补贴、违约扣多少钱）、参数和结果之间的关系（并发数和排队时间）、几种状态之间的切换（改之前和改之后）。

页面只是把正文换个样子再说一遍，或者一张图就能看清，就不做页面，说明原因，并建议改用 `zh-ladder-diagram`（讲解图）或 `zh-ladder-writing`（文字）。

## 2. 想清楚这页要让读者「试」什么

写下来（不放进页面）：

- 读者要回答的那一个问题，比如「我们公司能拿多少补贴」
- 读者能改的输入：哪几个，取值范围多大，默认值是什么。**只放会改变结论的输入**，最多三四个
- 输出怎么从输入算出来，每一步在原文哪里有依据
- 原文的哪些条件、例外会让结果突然变化（比如「专精特新企业门槛降为 10 万」），这些地方要让读者能拨到

计算规则写不出原文依据的，不做成交互，在页面上写明「原文未说明」。

## 3. 做页面

从 `assets/模板.html` 起手。它已经包含页面必备的结构，你填内容、写计算逻辑即可。结构说明见 `references/页面结构.md`，交互写法见 `references/交互模式.md`。

每页必须有：

1. **一句话结论**放在最上面，读者十秒能看懂。
2. **控件和联动的结果**：拖动或切换后，数字和图立刻变。
3. **先猜后看**：至少有一处让读者先选一个预期，再揭晓结果。这是交互页比文字强的地方，读者猜错的那一刻最容易记住。揭晓文字由计算函数生成，不要手写结论：手写的结论很容易和公式对不上。
4. **假设与依据**：每条计算规则写出原文出处；原文没说的写「原文未说明」。
5. **原文里对不上的地方**（有才写）：两处说法各是什么、页面按哪一处算。不要悄悄选一个。
6. **本页不能告诉你什么**：页面的局限，比如「未考虑地方配套政策」。
7. **来源**：打开过的链接；材料是本地文件时写文件名，不编链接。

技术约束：单个 HTML 文件，样式和脚本都内联；不依赖网络也能打开（需要公式时可以从 cdnjs 引入 KaTeX，但页面在离线时仍要能读）；不存任何数据；动态文字用 `textContent` 写入，不用 `innerHTML` 拼接。

## 4. 检查

1. 运行检查脚本。它在手机到桌面共 5 个宽度下截图，把每个滑块拨到两端、每组分段按钮逐个点一遍并各截一张，报出控制台报错、对外网络请求、横向滚动、文字溢出、手机上结论太长和按钮太小。分段按钮组要写 `role="group"`，脚本才找得到：

   ```bash
   python3 ${CLAUDE_SKILL_DIR}/scripts/check_page.py 页面.html --out 截图目录
   ```

   

2. **打开截图看**：至少看手机宽度、桌面宽度、以及滑块拨到两端的截图。结论有没有在第一屏？手机上控件能不能用？拨到极端值时数字和图是否合理？
3. **手算两个点**：挑两组输入，按原文规则手算一遍，和页面结果对比。尤其要算一个落在例外条件上的点。

没法运行浏览器时，直说「未做渲染检查」。

## 5. 交付

有发布页面的工具（比如 Artifact）就发布成可分享的页面；没有就交付 HTML 文件，告诉读者用浏览器打开。附一两句话说明这页能帮他回答什么问题、应该先拨哪个控件。
