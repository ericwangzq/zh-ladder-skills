# 中文受控写作

目标：读者读一遍就抓住要点，而且读到的意思和原文一致。

这两件事会互相拉扯。为了「清楚」，最常见的错误是改掉了原文的条件、确定程度或状态；为了「简洁」，最常见的错误是把段落切成一串短句，读起来反而更慢。本 skill 的规则都是为了同时守住这两头。

先读底线规则：`references/底线.md`。

## 用法

输入：命令后面的文字就是任务；要处理的材料（文件路径或粘贴的文字）没给就先问一句，不要自己找。

输出：改好的文字。写在回复里，用户要文件时再落盘，落点按底线第 6 条。

**路径约定**：本文里 `references/…`、`scripts/…` 都相对于**本 SKILL.md 所在的目录**（下称 skill 目录）。你的工作目录是用户的项目目录，不是 skill 目录，所以跑脚本必须用绝对路径：下面命令里的 `$SKILL_DIR` 指 skill 目录的绝对路径，**运行前把它换成实际路径**（加载本 skill 时已经给过你 SKILL.md 的位置）。shell 不会替任何人展开这个变量；省略目录的相对写法换个工作目录就找不到文件。

## 1. 先认清任务

不同任务要保留的东西不同，先判断属于哪一种：

| 任务 | 要做的 | 不能做的 |
| --- | --- | --- |
| 改写 | 保留全部信息（不是全部句子）：重排结构、合并重复、把过程压成结果 | 删掉条件、例外、数字 |
| 摘要（常有字数上限） | 只留影响读者判断的内容 | 为了凑字数丢掉改变结论的条件或风险 |
| 讲给外行 | 换成读者懂的说法，可以加类比 | 把类比当事实，把边界条件讲没了 |
| 汇报（工作结果、排查、会议） | 参考 `references/汇报模板.md` 组织 | 把「做了」写成「验证了」，把「倾向」写成「决定」 |

**篇幅也有目标**，没有字数上限时同样如此。改写得「简洁清楚」，一般是原文的 50%–70%；汇报和会议结论 30%–60%；讲给外行不超过原文。写长了，多半是重复了结论或复述了过程。原文本身信息很密、确实压不下来时，信息优先。

模板是起点，不是表格。内容放不进某一栏，就别硬塞：进展不是风险，建议不是决定。复盘、需求文档、评审意见这类没有现成模板的，按「先结论、再依据、再细节」组织即可。

用户要「严格」「全部规则」「简明技术中文」，或者文本是操作手册、步骤说明这类要逐句执行的内容时，再加上 `references/严格模式.md`。其他情况不用它：句长上限会把说明性的段落切碎，实测读起来更慢。

## 2. 动笔前列保真清单

把原文里这些东西列出来。原文超过约 1500 字时，写进临时文件（系统临时目录或用户指定的位置，不交付、也不放进用户的项目目录），第 4 步逐项打勾：长文的例外和矛盾很容易在动笔后忘掉，实测只在心里列，较弱的模型会漏掉定义和例外。短文在心里列即可。

- 数字和单位，以及它们前面的「约」「不超过」「以上」「预计」
- 条件、例外和适用范围，尤其是离规则很远才出现的例外
- 否定和双重否定
- 确定程度：预计、初步、估算、尚未验证、可能
- 归属和分歧：谁说的、谁反对、最后定没定
- 状态：提议、已决定、已完成、已验证
- 口径：含什么、不含什么
- 定义：原文给术语、级别、档位下的定义（比如 P0/P1/P2 各指什么）
- 拆分：总数下面的分项（26 个里 18 个已验收、8 个待反馈）
- 原文自己的矛盾：同一件事在两处说法不一致，以及**哪些结论建立在矛盾的数字上**

长文先通读一遍再列，例外和矛盾常常藏在后半部分。

## 3. 写

- **先给读者一个落脚点**。短文第一句给结论；一千字以上的长文，开头用三到五行写清现状、结论和待决事项，再展开。汇报给状态，摘要给判断，解释给答案。
- **重新组织，不要顺着原文逐段改句子**。原文的顺序（会议流水、时间线、「方案 → 数据 → 意见 → 结论」）是作者写的顺序，不是读者用的顺序。按读者要做的事排：先结论，再影响结论的条件和风险，再细节。规则和它的例外放在一起写，不要隔开。
- **每件事只说一次**。开头已经给了结论，正文就不再整段重复；某条评审意见后来成了结论，在意见后面标一句「→ 已列为上线前提」，不要在文末再抄一遍结论清单。原文的附录、批注、作者自评，并到正文对应的位置，一两句说清。
- **过程压成结果**。「甲提出、乙回应、丙补充」的来回，写成最后的立场和仍然存在的分歧；agent 日志的逐条时间线，写成做了什么、结果怎样、卡在哪。原话只在措辞本身带信息时保留，比如「原则上可以」表明主管部门没有把话说死。
- **句子自然就好**。不追求短句；一个完整的意思放在一句里，比切成三句、每句重复主语更好读。几个对象要横向比较、或每项都带数字时，用表格。
- **讲给外行时，说人话**。术语第一次出现就用一句话解释；读者关心「这对我意味着什么」时，可以按原文条件算一个例子，标明「按原文条款推算」。
- **删空话，不删信息**。「进行＋动词」「不是…而是…」、营销腔、套话开头和收尾，删掉或换成直接说法，具体见 `references/空话清单.md`。定义、分项、日期、条件都是信息，再短也不删。拿不准一句话算不算信息时，留着；但背景铺垫、重复和讨论过程不在此列。
- **原文的矛盾要点出来**，例如「正文写 71 条，汇总表写 77 条，需核实」。不要自己挑一个。依赖这个数字的结论也要一起打上问号。
- **不加原文没有的事实**：不补原因、日期、选项、建议，不把「希望」写成「计划」。
- **摘要有字数上限时**，先保住「改变结论的条件、风险、矛盾」，再保数字。字数按汉字、字母、数字和标点计，空白和 Markdown 符号不计；对比脚本会报新稿字数。省略了会影响决策的内容时，用一句话说明省了什么。

## 4. 交付前核对

1. 有原文时，运行对比脚本，看哪些数字、确定程度词、条件词和否定词在新稿里不见了：

   ```bash
   python3 "$SKILL_DIR/scripts/fidelity_check.py" 原文文件 新稿文件
   ```

   做摘要时在末尾加 `--summary`，脚本就不再逐条列出省掉的数字，只报单位、确定程度、条件和否定的变化。
2. 看篇幅：脚本会报新稿是原文的百分之几。超出第 1 步的目标，就找重复的结论和复述的过程删掉，再跑一次脚本，确认删掉的不是信息。
3. 对照第 2 步的清单（长文就是那个临时文件）逐项打勾。脚本查不出的东西都在这里：条件挪了位置、适用范围变宽变窄、「张三认为」变成了「已决定」、定义和分项被删了、原文矛盾标了但依赖它的结论照搬了。
4. 读开头：读者只看第一句，会不会误解？只看开头三五行，能不能知道结论、前提和要他做的事？

**脚本能查什么、查不了什么**——搞清这条才知道第 3 步为什么不能省。它比的是字面：数字和单位、限定词（预计、约、尚未）、条件和例外词、否定词、归属和状态词在新稿里还在不在，以及新稿有没有原文没给过的数字。

它查不出意思变了。人物归属互换、例外从甲条件挂到乙条件、「不超过 3 天」写成「3 天内」、「含税 12 万」写成「12 万」，在脚本眼里都是词还在。反过来，条款编号、表格序号会误报。**既有误报也会漏报，所以它只是提醒，不是判决：逐条看它报的项，是有意省略就跳过，是丢了就补回；退出码为 0 不代表意思没变。**

核对过程不写进输出。只交付改好的文字；发现了原文矛盾或需要读者确认的事，写在正文里或末尾。
