# 汇报模板

用于：把 agent 的工作记录、任务结果、排查过程、会议讨论整理成给人看的汇报。

读汇报的人常常一边做别的事一边看，也可能不记得上下文。所以状态要一眼看清，而且每个状态只有一种读法。

> 本文件的状态词和模板改编自 [dualface/ste-zh](https://github.com/dualface/ste-zh)（MIT）。改动：去掉了句长上限和「每句一事」，加了会议结论模板。

## 状态词

写工作状态时只用这 10 个词，每个都要配上明确的范围：

| 状态词 | 什么时候用 |
| --- | --- |
| 已完成 | 范围内的事全部做完 |
| 部分完成 | 做了一部分，写清做了哪些、没做哪些 |
| 未开始 | 还没动 |
| 进行中 | 正在做 |
| 已验证 | 做过检查，写出检查方法和结果 |
| 未验证 | 没做检查 |
| 失败 | 做了，结果不对；附关键报错原文 |
| 跳过 | 有意不做，写原因 |
| 阻塞 | 卡在某个条件上，写卡在哪 |
| 未确认 | 缺证据，不知道是不是；写怎么确认 |

两条最容易错的：

- **工作状态不等于验证状态。** 代码改完是「已完成」，测试跑过才是「已验证」。
- **转述不等于验证。** 「据供应商称支持」是转述，不是你验证过。照原样写「据供应商称」。

不用「应该没问题」「大概率」掩盖不确定，直接写「未确认」，再写怎么确认。

## 结果汇报

```markdown
<状态词>：<完成范围和结果，一句话>。

**结果**
- <关键结果，带数字>

**验证**
- 已验证：<检查方法和范围> — <结果>
- 未验证：<没做的检查> — <原因>

**没做的和遗留问题**
- <事项> — <原因或影响>

**需要你决定**
1. <选项>（推荐）— <后果>
2. <选项> — <后果>
```

没有内容的节删掉。

## 排查结论

```markdown
<原因是什么；没查清就写「原因未确认」>。

**现象**：<看到了什么>
**原因**：<有证据的原因；证据不足时写「未确认」和确认方法>
**证据**：<路径:行号、日志原文、数据>
**影响**：<范围、数量、持续时间>
**下一步**：<动作、负责人、时间>
```

多人对原因有不同看法时，分别写出各自的判断和依据，以及最后是否有定论。不要替他们统一。

## 会议结论

给没参会的人看。核心是让他分清哪些定了、哪些没定。

```markdown
<一句话：这次会定了什么，最重要的未决事项是什么>。

**已决定**
- <决定>（<谁拍板，或「一致同意」>）

**未决定**
- <事项>：<A 的意见> / <B 的意见>。<下一步怎么定，谁定，什么时候>

**待办**
| 事项 | 负责人 | 时间 |
| --- | --- | --- |

**需要你知道的风险**
- <风险>
```

「方向上同意」「原则通过」「倾向于」不等于「已决定」。原文怎么说就怎么归类：原文没有明确拍板的，放进「未决定」，并照抄原文的说法。

## 请求决定

```markdown
<一句话写要决定什么>。

1. <动作>（推荐）— <后果>
2. <动作> — <后果>
```

推荐项放第一。每项写清选了它会发生什么。
